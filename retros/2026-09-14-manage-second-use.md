# Retrospective: 4 L's

Period: second use of manage, 14 September 2026, including the correction of its premature release placement
Place: this repository

## Liked

- The correction separated exclusion from assignment: work can belong to
  neither the current release nor a named future release yet.
- Exact CI runs confirmed that the Windows delay is real and current without
  turning a transient duration into durable plan truth.
- The requirement's advisory-only constraint made clear what it contributes:
  diagnosis, not an optimization or a release outcome.

## Learned

- "Not in 0.0.2" does not imply "in 0.0.3". A later release exists only when
  its promise can be stated and the admitted work advances that promise.
- Clearing a current block is not the only reason to admit work. Diagnostic
  or enabling work may belong when it advances the release promise, but this
  requirement only locates a cost and 0.0.2 promises consumer-visible method,
  test ownership, and seat dependencies.
- Persistent Windows delay affects the current delivery loop, but measurement
  alone does not shorten it and the requirement deliberately chooses no
  remedy. That supports leaving it unassigned, not parking it elsewhere.

## Lacked

- The manage skill defines dependency order but not the test for honest
  release placement.
- The first decision treated the absence of contribution to 0.0.2 as enough
  evidence for a future assignment.
- No accepted later scope in the tree can yet support a coherent promise, so
  there is no honest later release to name.

## Longed for

- A future manage move could keep accepted work visibly unassigned until a
  release promise earns it.
- Release placement could ask both questions explicitly: what promise does
  this advance, and why now rather than merely not now?
