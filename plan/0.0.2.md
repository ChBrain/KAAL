# Plan: 0.0.2

The first plan in this tree, and the first artefact of the manager's seat. It
orders work across the seats and writes none of it: every item names the seat
whose diff it is, and a plan that says what somebody else must do is still a
plan and never their diff.

## The promise

0.0.1 published `@chbrain/kaal` with `files: ["bin"]`, so what a consumer
installs is the deterministic command surface alone. The package is the
primary one and carries everything an embedded consumer needs, which is the
tool and the skills and the agents together; sub packages are carved out
later, when a piece demonstrably travels on its own, and a consumer who takes
one is choosing to take less rather than being asked to assemble more.

So 0.0.2 promises three things a reader can check. Install the package and
you have the method, not a quarter of it. Open `tests/` and you find the whole
of it, five kinds, with every case sitting in the lane of the seat that owns
what it proves. And open any seat's lane and you can read what it needs from
which other seat before it can move.

## What a seat needs from a seat

The table is doctrine and belongs in `AGENTS.md`: it is the same on every
task, it names the only question one seat may put to another, and it is what
keeps an ask inside a lane instead of becoming an edit in someone else's
tree. What changes per task is which of these edges is live, and that is what
a seat's own plan records.

Each seat's work exists only when a specific upstream artefact is in a
specific state, and is blocked by a state it cannot change itself.

| seat      | work exists when                                                 | blocked when                                             |
| --------- | ---------------------------------------------------------------- | -------------------------------------------------------- |
| analyst   | an ask has no requirement, or a closed criterion is contradicted | only a person can answer                                 |
| architect | a requirement has no drawing                                     | the criterion cannot be drawn as written                 |
| developer | a test is red                                                    | the red test needs a seam that does not exist            |
| tester    | a criterion has no proof, or a proof has no fresh record         | a verify or validate fails for a reason outside `tests/` |
| operator  | something is proved and unshipped                                | a control outside the tree                               |
| manager   | two seats are clear and the order is not obvious                 | never on its own account                                 |

The manager cannot be blocked by a seat, only by proxy, carrying somebody
else's block. That is why it is the seat that picks blocks up, and it is the
argument against seats handing work to each other directly.

Three rules hold the whole of it:

- **A seat names the block and never the fix.** The blocked seat says where,
  the manager says when, the owning seat says what. None of the three may
  decide for another, which is why neither a block nor the manager's pick-up
  carries a field for a remedy.
- **A refusal is a block.** Every time a seat tries to write outside its lane,
  that is the moment to record one, and the wall that refuses it already knows
  which seat owns the path.
- **A bug blocks its retest.** A failing verify or validate is recorded as a
  bug naming the earliest of requirements, architecture, code or operations
  where it can be fixed, and the case it blocks is not retested until it
  clears.

## The order

### 1. A promotion names what it refuses

- Delta: the asker's rule is that the tester may turn a target red and CI may
  not, and one target cannot be both. Today there is one, so the licence a red
  test already has (`not delivered` is an answer and the wall stays green)
  lives on the same branch a consumer installs from.
- First rather than last, and that is this revision. The asker's words are
  that branches reach a release branch and release reaches main never red,
  which is wider than the two verdict gates below: it is the whole board, and
  it says where a red one may stand. Item 2 cannot be done without it. A unit
  moving beside its module is a file the developer adds and a line the tester
  writes naming it, the suites wall reports a test file no suite names, and
  the two are two lanes. File first is a red board and line first names a file
  that is not there, so on one target the move is impossible and on two it is
  a red release branch for one merge. Twenty-one times.
- Seat: analyst, then the chain, then governance for the workflow, and Kai for
  the branch and its protections, which are item 9's kind of control.
- Needs: nothing in the tree. It rests on `kaal runs`, which is stable, and
  not on the suite layer.
- Action: a release branch between, and two gates rather than one. A branch
  reaching release refuses `regressed` and `nothing ran`, which both mean a
  claim that was true and is not. Release reaching main additionally refuses
  `not delivered`, which is the one a tester is allowed to leave standing. The
  strict gate is late rather than early on purpose: red is allowed to exist
  and is refused publication, rather than kept out of the tree where nobody
  sees it.
- And the board itself is judged the same way round. A wall may stand red on
  `release`, where the seat that can fix it is still working and can see it.
  No wall may stand red on the promotion to main. So a diff that leaves a wall
  red is a diff that may be merged and may not be published, which is the
  licence the verdicts already give a task and the board has never had. A wall
  red on `release` is not a licence to leave it red: it is a block, with an
  owner, and the promotion is what refuses to forget it.
- Evidence: a tree carrying one `not delivered` task reaches release and is
  refused main, naming the task. The four verdicts already compute this, so
  the branch is a place and a rule rather than a mechanism.
- Three of the four protections are walls rather than settings. That main
  accepts only from release is a check reading the pull request's head branch,
  deterministic and offline and in the tree; so are both verdict gates, which
  are `kaal runs` plus a condition on the base branch. What must be a setting,
  and is therefore Kai's: a pull request required on `release` and on `main`
  with no direct push, force push and deletion blocked on both, and the checks
  marked required so a red one stops a merge. Four rows in a ruleset, joining
  item 9's list rather than becoming a new kind of problem.
- Carries a governance diff that must land the same day: a lane branch is cut
  from `release` and no longer from `main`, which is a sentence in `AGENTS.md`
  and in `CLAUDE.md`. Written a day late, the next branch comes off the wrong
  base and the first merge is a conflict nobody caused.
- Each piece starts at the rung it can reach and is named with where it is
  going, because the ladder runs human, then the pages, then a skill, then a
  wall. The two verdict gates start at the wall, since `kaal runs` already
  computes them and a thing that can be a wall today has no business being a
  sentence. The branch a lane is cut from starts as the pages and hardens once
  a diff is refused for coming off the wrong base. The four ruleset rows start
  at the human and stay there until the tree can read them, which is item 9's
  standing complaint and not this item's to solve.
- Unblocks: item 2, which cannot be split across two lanes without it, and
  item 13, which is the first promotion this rule judges.

## Placed for 0.0.3, by the asker

Three wants have been placed in a release by the person who owns the
priorities, and they are written here rather than left in a conversation
because a want nobody can read is a want nobody can plan. None of them is
stated yet: each is an ask, and the analyst judges it into a requirement with
a proof or refuses it with the reason, which is what `AGENTS.md` now says an
idea does before it reaches this file.

- **The league learns while it moves.** Ten unconsumed retros on one skill is
  the analyst's next ask, the rule is in `skills/analyse/SKILL.md` and in
  `AGENTS.md`, and nothing enforces it: `kaal retros` answers `analyse: 41
unconsumed` and exits 0. What the four lenses produce is the engine's own
  improvement, and what survives the analyst's reading is a requirement no
  plan names yet, which is the backlog and needs no sixth kind of page. The
  asker's design is a ratchet rather than a line at ten: red where unconsumed
  grows, or above a starting number each release lowers. A wall that fires at
  ten today would be red on four skills at once with ninety-six retros between
  it and green, and a wall nobody can satisfy is a wall people read past. It
  bites as every wall bites, red on `release` and refused at the promotion,
  and not by refusing a lane's entry to `release`: that would couple every
  seat's throughput to the analyst's queue, which is the coupling the lanes
  exist to avoid. The asker's words, and they are the shape of the ask rather
  than its criteria.
- **The release and the regression plan are two plans, and regression is
  derived.** `main` is the current release and `release` is the next one.
  `main` enforces both plans at once; `release` enforces regression as a hard
  wall and lets the release plan's wall stand red, which is the licence. So a
  wall binds or does not bind per wall and per target, where today `binding`
  is one boolean per target, and that is a sixth seam over the five
  `a-plan-picks-its-suites` draws.
  What regression holds is not last release's release plan. A release changes
  requirements as well as adding them, and a changed requirement's old cases
  are exactly the ones that must not be enshrined: the behaviour they hold was
  deliberately replaced. The tree already carries that distinction and nothing
  reads it for this. A requirement that supersedes another is a change; one
  that supersedes nothing is an addition. So regression has a definition and
  not a list: the cases of requirements delivered in a released version and
  not superseded since, which drops a requirement the moment its replacement
  is stated.
  Derived rather than written, because derived is deterministic, and that is
  the ladder rather than a change of mind: a plan naming its suites by hand is
  the pages rung, and a selection the board computes is the wall. 0.0.2 builds
  the first; this builds the second over it. What survives the move is every
  reader `a-plan-picks-its-suites` draws, because only where the set of suites
  comes from changes.
- **A target that moved alone says so.** `main` can move without `release`, by
  a hotfix, and nothing in the tree reads the pair or says which way the sync
  goes. The asker's shape is a pull request from `main` into `release` where
  they are out of step. It is a different question from a promotion being
  asked for, which is why it is not a criterion of
  `a-promotion-names-what-it-refuses`.
- **The evals could run.** `evals.yml` reads `EVALS_API_URL`, `EVALS_API_KEY`
  and `EVALS_MODEL` and refuses in one line when they are missing, and the
  reason they are missing was the cost of the calls. The asker reports a
  runtime where that cost is near zero. Two models on one fixture took an
  afternoon by hand this week; every fixture on every skill is a workflow run.
  That is what would make a move's evidence its own rather than its skill's.
